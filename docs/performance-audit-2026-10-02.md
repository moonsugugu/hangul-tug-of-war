# 줄다리기 성능 점검 — 2026-10-02

## 확인한 문제와 수정

각 입력마다 학생 전원의 전체 상태를 다시 만들고 전송했다. 공통 상태와 JSON을 재사용하고 일반 방송을 방별 60ms로 묶어 변경 필드만 보낸다. 답한 학생의 다음 문제, 화면 단계 전환, 릴레이 결과는 즉시 전달한다. 소켓의 플레이어 조회는 Map 직접 조회로 변경했다. 선생님을 학생 30명 정원에서 제외했다.

공통 보호: 압축 창 13비트·memLevel 7·동시 압축 4개, 연결당 입력 한도(초당 20회·순간 40회), 256KiB를 넘는 전송 대기열은 연결을 종료한다. 느린 연결의 종료 정책은 오래된 패킷이 메모리에 쌓이는 것을 막는다. IP 제한은 추가하지 않았다. 구형 화면은 전체 상태를 받고 새 화면만 delta를 사용한다. 개인 상태가 다른 학생에게 섞이지 않는지, 값 삭제(null), 새 연결의 전체 상태, 화면의 delta 병합을 회귀 검사했다.

## 검증

- npm test와 npm run build 통과.
- 로컬 실제 WebSocket: 학생 30명 + 교사 1명, 준비 후 6초 측정, 압축된 TCP 수신 바이트 기준 반당 **0.170Mbps**. 좌표 게임은 100ms마다 이동하고 문제 게임은 500ms마다 답안을 제출했다.
- 재현: 저장소에서 `node scripts/measure-load.mjs`. 1Mbps를 넘으면 실패한다. `load-metrics.mjs`는 이 시험에서만 사용한다.

- 수정 전 29명+교사 시험 0.926Mbps, 수정 후 30명+교사 시험 0.170Mbps. 문제 순서와 라운드 진행은 무작위이므로 정밀한 동일 작업량 CPU 비교로 해석하지 않는다.

이는 로컬 짧은 시험과 상태 처리 비교 결과다. 운영 노트북의 전체 CPU 사용률이나 600명 장시간 동시 접속 수용량을 보장하지 않는다. 전체 상태가 작은 축구·티볼에서는 작은 delta의 메타데이터와 비교 비용 때문에 모든 상황에서 전송량·CPU가 줄어드는 것은 아니다. 반복 방송의 최대 빈도, 압축 메모리, 느린 연결의 대기열을 제한하는 효과가 중심이다.

## 서버 조건

데이터는 휘발 상태로 각 방의 서버 메모리에만 둔다. DB·학습 기록 저장 방식은 변경하지 않았다. 기존 방별 WebSocket 경로와 포트를 사용하고 기본 바인딩은 127.0.0.1이다. 새 서비스·포트·PM2·터널 등록은 필요 없다. 재시작하면 방이 사라지는 기존 운영 방식은 같다. 영구 기록을 추가할 경우 api.moonsunezip.com의 기존 데이터 API를 사용해야 한다.
